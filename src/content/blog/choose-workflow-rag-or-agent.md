> 本文是《AI Agent 实践》系列第 2 篇。上一篇实现了[最小工具调用循环](/blog/build-minimal-ai-agent-with-typescript/)，这一篇先不增加工具，而是回答一个更重要的问题：这个功能真的应该使用 Agent 吗？

做 AI 应用时，我发现最容易被忽略的不是 Prompt 怎么写，而是架构选择。

一个需求里只要出现“用户用自然语言输入”，大家就很容易顺手画出 Agent：模型先思考，再查知识库，再调用几个工具，最后生成答案。图看起来很完整，实际落地后却可能比一个普通表单更慢、更贵，也更难测试。

Agent 解决的是**执行路径不能完全预先确定**的问题。它并不是普通函数、工作流和 RAG 的升级版，这几种方案解决的是不同问题，而且经常需要组合使用。

## 从一个数据分析需求开始

假设我要给数据工作台增加一句话分析功能：

> 上传一份销售表，然后按月份和渠道统计销售额，找出下降最明显的渠道。

这个需求可以被实现成很多形态：

1. 做一个表单，让用户选择维度、指标和筛选条件。
2. 固定执行“识别字段 → 聚合 → 排序 → 生成图表”的工作流。
3. 检索一份指标口径文档，再帮助用户理解“销售额”的业务定义。
4. 让模型根据用户目标决定是否查看字段、执行哪种聚合、是否继续追问。

四种方案都可能合理，区别在于真正的不确定性在哪里。

如果用户只是嫌配置表单麻烦，模型只需要把自然语言转换成结构化配置，后面的计算步骤完全可以固定。这时核心并不是一个“自主 Agent”，而是一个带 AI 解析能力的确定性工作流。

如果不同任务需要选择完全不同的工具和路径，例如先查看数据质量、再决定清洗还是聚合、过程中还可能向用户补问信息，Agent 才开始体现价值。

## 普通函数：规则能够直接写清楚

当输入、输出和规则都明确时，优先使用普通函数。

例如聚合函数：

```typescript
interface Measure {
  field: string;
  aggregation: 'sum' | 'count' | 'avg' | 'min' | 'max';
}

function aggregate(rows: DataRow[], measure: Measure) {
  // 确定性计算：相同输入必须得到相同输出。
}
```

金额求和、权限判断、日期格式化、字段类型检查，都不需要模型“推理”。把这些逻辑交给模型，不仅更贵，还会失去精度、边界和可重复性。

适合普通函数的信号包括：

- 规则能用代码完整表达。
- 相同输入应该始终得到相同输出。
- 每一步都要求精确。
- 失败条件和错误信息可以预先列举。
- 不需要理解开放式自然语言。

在 Agent 应用里，普通函数并没有消失。相反，它们会成为工具、校验器、权限策略和领域引擎，是系统里最可靠的部分。

## 工作流：路径固定，但步骤较多

工作流适合“步骤多，但顺序能够提前确定”的任务。

例如上传 CSV 后：

```text
解析文件
  → 推断字段类型
  → 校验必填字段
  → 执行聚合
  → 生成图表数据
  → 导出结果
```

每个节点都可能失败，也可能需要重试和记录状态，但下一步并不需要模型临时决定。使用状态机、任务队列或工作流引擎会比 Agent 更容易保证：

- 顺序不会乱。
- 某个节点可以安全重试。
- 失败后可以从固定位置恢复。
- 每条路径都可以写自动化测试。
- 成本和耗时比较稳定。

模型仍然可以出现在某个节点里，例如“把自然语言转成 PivotConfig”或“根据统计结果生成摘要”。但局部使用模型，不代表整个流程就是 Agent。

我更喜欢把这种架构称为：

> 确定性工作流，包含少量概率性节点。

很多所谓 Agent 产品其实用这种方案就够了，而且通常会更稳。

## RAG：解决知识从哪里来

RAG 的核心是检索外部知识，并把相关内容提供给模型。它回答的是：

> 模型生成答案时，需要参考哪些它原本不知道的内容？

例如用户问：

> 公司报表里的“有效销售额”是否包含退款订单？

模型不能只靠通用知识回答，需要检索公司的指标口径文档。一个典型 RAG 链路是：

```text
用户问题
  → 查询改写
  → 检索指标文档
  → 重排与裁剪
  → 携带引用生成答案
```

RAG 本身不要求模型动态调用多个工具，也不一定包含循环。一次检索、一次生成完全可以是固定工作流。

同样，Agent 也可以把“搜索知识库”注册成一个工具，在需要时主动检索。因此 RAG 和 Agent 不是二选一：

- RAG 负责提供知识。
- Agent 负责在多个可能动作之间选择下一步。
- 工作流负责约束确定的执行顺序。

把这三个概念混在一起，往往会导致系统职责不清：检索不准时不知道该改索引还是改 Prompt，执行失败时又不知道是 Agent 选错工具还是工作流状态错误。

## Agent：下一步确实无法提前写死

当任务只有目标，没有稳定路径，并且模型必须根据中间结果继续选择动作时，Agent 才是合适的抽象。

例如：

> 检查这份数据为什么本月利润异常，如果能定位原因，就给出可验证的分析结论。

可能的执行路径包括：

```text
查看字段
  → 检查缺失值
  → 对比上月
  → 按区域下钻
  → 发现华东成本异常
  → 再按产品下钻
  → 输出结论和证据
```

另一份数据可能在“检查缺失值”时就发现导入错误，需要直接向用户澄清。路径依赖中间观察结果，很难提前枚举完整，这正是 Agent 的优势。

适合 Agent 的信号包括：

- 用户给出的是目标，不是明确步骤。
- 工具很多，但每次只需要其中一部分。
- 下一步依赖上一工具的结果。
- 允许系统在有限范围内探索。
- 错误成本可控，或者能够增加人工确认。
- 任务价值足以覆盖额外延迟和模型成本。

反过来，如果路径只有唯一一条，Agent 循环只是把固定代码改成了不稳定的模型决策。

## 四种方案的判断表

可以先用一张表做初筛：

| 主要问题                       | 更适合的方案        | 原因                     |
| ------------------------------ | ------------------- | ------------------------ |
| 精确计算、格式转换、权限判断   | 普通函数            | 规则明确且必须可重复     |
| 多步骤但顺序固定               | 工作流              | 易重试、恢复和测试       |
| 模型缺少私有或最新知识         | RAG                 | 重点是找到可信上下文     |
| 路径依赖中间结果               | Agent               | 需要动态选择下一步       |
| 固定流程中只有一个自然语言入口 | 工作流 + 结构化输出 | 不必引入自主循环         |
| 开放任务需要检索和多个工具     | Agent + RAG + 工具  | 三者承担不同职责         |
| 高风险写操作                   | 工作流 + 人工确认   | 不应由模型直接获得执行权 |

真正的项目通常落在最后几行：不是选一个名词，而是把不同不确定性放进合适的边界。

## 用三个维度做更具体的判断

### 1. 路径是否可预测

先尝试把流程画出来。如果每个条件分支都能明确写成代码，通常优先工作流。

只有当分支数量庞大、依赖开放式语义，或者工具组合无法合理穷举时，才把“选择下一步”交给模型。

### 2. 错误成本有多高

“选错一篇参考文档”与“给客户退款两次”不是同一等级的问题。

错误成本越高，模型能直接控制的范围就应该越小：

```text
低风险：允许自动探索
中风险：生成计划，应用校验后执行
高风险：只给建议，用户确认后由工作流执行
```

是否使用 Agent，不只取决于模型能不能做，还取决于做错后能不能承受。

### 3. 结果能否验证

数据聚合可以用代码复算，文件是否存在可以直接检查，这些任务即使使用 Agent，也有明确验证器。

“这段品牌文案是否足够打动人”就很难自动判断。结果越难验证，越不适合给 Agent 过高自治权，应该增加人工审阅或缩小任务范围。

## 数据分析 Agent 应该怎样拆

回到开头的需求，我不会把整条链路都交给模型，而会这样分工：

| 环节               | 负责方               | 原因                     |
| ------------------ | -------------------- | ------------------------ |
| 文件解析           | 确定性代码           | 格式和错误可以精确处理   |
| 字段类型推断       | 代码为主，用户可修正 | 结果需要稳定、可查看     |
| 理解自然语言目标   | 模型                 | 涉及开放语义和字段别名   |
| 生成 PivotConfig   | 模型                 | 将意图映射成领域动作     |
| Schema 与字段校验  | 确定性代码           | 防止不存在字段和非法聚合 |
| 执行透视计算       | 本地引擎             | 保证精度、性能和隐私     |
| 解释聚合结果       | 模型                 | 适合组织自然语言         |
| 保存模板、导出文件 | 工作流               | 有副作用，需要固定步骤   |

最后得到的不是一个“什么都能做”的 Agent，而是一套混合架构：

```text
                       ┌──────── 指标知识库（RAG）
                       │
用户目标 → 模型规划 ───┼→ 结构化领域动作
                       │          ↓
                       │      校验与权限策略
                       │          ↓
                       └────→ 确定性工具 / 工作流
                                  ↓
                              可验证结果
                                  ↓
                           模型解释与呈现
```

模型负责消化模糊语义，代码负责事实、规则和副作用。这条边界越清晰，系统越容易测试。

## 两个常见失败方向

### 为了展示自主性，删除固定边界

例如本来只需要“选择字段并聚合”，却给模型一个 `run_javascript` 工具，让它自己写代码处理整份数据。Demo 看起来灵活，实际会同时失去类型校验、性能控制、数据安全和结果可重复性。

灵活并不等于开放无限能力。更好的做法是提供领域工具，例如 `run_pivot`、`compare_periods` 和 `profile_data_quality`。

### 用 Prompt 掩盖架构问题

如果模型总是跳过必要步骤，有时不是 Prompt 不够强，而是这个步骤本来就不应该由模型决定。

例如所有分析都必须先验证字段，那就把校验写成工作流的强制节点，而不是在 system prompt 里反复强调“请务必先检查字段”。确定规则应该由代码表达。

## 建立一个非 Agent 基线

决定使用 Agent 后，最好仍然保留一个更简单的基线版本。

对于数据分析场景，基线可以是：

```text
自然语言 → 一次结构化输出 → 校验 → 固定计算 → 生成结果
```

再将 Agent 版本与它比较：

- 任务完成率是否真的更高？
- 多步探索解决了哪些基线无法解决的任务？
- 平均延迟和 Token 增加多少？
- 错误路径是否更难恢复？
- 用户是否理解系统正在做什么？

如果 Agent 只让架构更复杂，却没有提高任务覆盖率，就应该退回简单方案。技术选择的目标是解决问题，不是保住“Agent”这个标签。

## 最后

普通函数、工作流、RAG 和 Agent 不是一条从低级到高级的进化路线：

- 函数负责确定规则。
- 工作流负责确定路径。
- RAG 负责补充知识。
- Agent 负责有限范围内的动态决策。

一个可靠的 Agent 应用，往往不是把一切都交给模型，而是只把真正需要语义判断的部分交给它。
