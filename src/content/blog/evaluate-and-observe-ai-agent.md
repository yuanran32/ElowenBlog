> 本文是《AI Agent 实践》系列第 8 篇，也是第一季收尾。上一篇建立了[人工确认与安全边界](/blog/human-in-the-loop-agent-security/)，最后要回答：怎样证明这套系统不只是偶尔演示成功？

普通函数测试通常有明确输入和输出。Agent 却可能为了同一个目标选择不同工具、走不同路径、使用不同表达，最终答案看起来都“差不多”。这很容易让评测退化成一种感觉：多试几次，答案看起来不错，就认为可以上线。

但真正进入产品后，用户不会只提交演示里的那一句话。模型版本、Prompt、工具说明、字段目录和业务规则也会不断变化。没有稳定评测，团队很难回答：

- 新 Prompt 到底更好，还是只在一个案例上更好？
- 最终答案错误，是计划错、工具错，还是解释错？
- 模型升级后，为什么工具调用次数突然翻倍？
- 失败率没有变化，为什么用户觉得系统变慢了？
- 安全拦截降低，是模型更听话了，还是权限规则被绕过了？

Agent 评测的核心不是给最后一段文字打一个总分，而是把运行拆成可以观察和验证的层次。

## 先定义“成功”是什么

以本季的数据分析 Agent 为例，用户输入：

> 只看华东地区，按月份和渠道统计销售额，找出环比下降最大的渠道。

一次成功至少包含：

1. 正确理解“华东”“月份”“渠道”和“销售额”。
2. 生成合法且符合指标口径的计划。
3. 没有读取手机号等无关敏感字段。
4. 调用正确工具，没有无意义重复。
5. 本地引擎计算结果正确。
6. 报告里的数字来自实际计算事实。
7. 遇到字段歧义时先澄清，而不是猜测。
8. 延迟、Token 和工具步骤没有超出预算。

如果只看最后一句是否通顺，前面七层的错误都可能被自然语言掩盖。

## 建立统一运行轨迹

可观测性的基础是一条结构化轨迹。每次运行都应该有稳定 `runId`，每一步拥有独立事件和关联 ID。

```typescript
interface RunTrace {
  runId: string;
  scenarioId?: string;
  model: {
    provider: string;
    name: string;
    configurationVersion: string;
  };
  startedAt: string;
  completedAt?: string;
  status: 'completed' | 'failed' | 'cancelled';
  terminationReason?: string;
  events: TraceEvent[];
  usage: RunUsage;
}

interface RunUsage {
  inputTokens: number;
  outputTokens: number;
  modelCalls: number;
  toolCalls: number;
  retries: number;
  totalLatencyMs: number;
  estimatedCost?: number;
}
```

事件不要只有一段自由文本日志，而应记录稳定字段：

```typescript
type TraceEvent =
  | {
      type: 'model.completed';
      step: number;
      durationMs: number;
      decision: 'answer' | 'tool';
      toolName?: string;
      usage: TokenUsage;
    }
  | {
      type: 'tool.completed';
      step: number;
      callId: string;
      toolName: string;
      durationMs: number;
      outputRef?: string;
    }
  | {
      type: 'validation.failed';
      step: number;
      issues: ValidationIssue[];
    }
  | {
      type: 'policy.decided';
      step: number;
      actionHash: string;
      decision: 'allow' | 'confirm' | 'deny';
    };
```

结构化事件让我们可以查询“最近一周 `FIELD_NOT_FOUND` 增加了多少”，而不是在几千条字符串日志里搜索近似文案。

## 可观测性不等于保存所有内容

完整 Prompt、原始工具返回和用户数据很有调试价值，也可能包含大量隐私。

日志应按用途分层：

| 层级       | 保存内容                             | 用途                   |
| ---------- | ------------------------------------ | ---------------------- |
| 指标       | 状态、耗时、Token、错误码            | 聚合监控，保存时间较长 |
| 结构化轨迹 | 工具名、校验结果、动作哈希、数据版本 | 定位执行路径           |
| 脱敏样本   | 经过授权的输入输出片段               | 深度调试与评测         |
| 原始内容   | 默认不保存或短期加密保存             | 仅在明确授权场景使用   |

手机号、令牌、邮件正文和原始数据行不应该为了“方便排查”默认进入日志。可以记录字段数量、内容哈希、对象存储引用和脱敏摘要。

可观测性要帮助理解系统，而不是创造另一个数据泄漏面。

## 把评测拆成六层

### 1. 计划正确性

检查模型是否把用户目标映射成正确领域动作：

- 行列维度是否正确。
- 指标和聚合方式是否正确。
- 筛选条件是否完整。
- 时间范围是否符合用户表达。
- 存在歧义时是否选择澄清。

这层通常可以对规范化后的 `PivotPlan` 做代码断言。

### 2. 工具轨迹正确性

检查 Agent 是否采用合理路径：

- 是否先获取必要字段目录。
- 是否调用了正确工具。
- 是否调用未授权工具。
- 是否重复执行相同动作。
- 工具失败后是否采取符合错误语义的下一步。

最终答案可能正确，但如果中间多调用五次昂贵工具，仍然属于回归。

### 3. 执行结果正确性

确定性引擎应该使用确定性测试：

- 小数据集手算结果。
- 空值和零基线处理。
- 金额精度和日期边界。
- 筛选、排序与总计。
- 数据版本变化时拒绝旧请求。

这层不要交给模型评分。能用代码精确断言的结果，就不应该用“看起来合理”代替。

### 4. 回答忠实度

报告中的每个数值和结论是否受到事实支持：

- 引用的 `factId` 是否存在。
- 文中数值是否与事实一致。
- 是否把相关性写成因果关系。
- 是否忽略结果截断、数据缺失等警告。
- 是否声称完成了工具从未执行的动作。

数值与引用可以由代码检查；语气、完整性和解释质量再交给人工或评分模型。

### 5. 安全与策略正确性

检查：

- 未授权字段是否始终不可见。
- Prompt injection 是否无法获得额外工具。
- 写操作是否进入确认状态。
- 被拒绝动作是否停止。
- 确认后参数变化是否使批准失效。
- 重复幂等键是否只产生一次副作用。

安全评测的目标不是模型“愿不愿意拒绝”，而是即使它不拒绝，执行器也能拦住。

### 6. 产品与工程指标

最后衡量用户实际体验：

- 任务完成率。
- 首次成功率。
- 澄清后成功率。
- 平均步骤数和无效工具调用率。
- P50 / P95 端到端延迟。
- 取消生效耗时。
- 单次任务 Token 与成本。
- 用户人工接管率。
- 用户修改计划的比例。

模型质量只是体验的一部分。工具慢、状态不清和确认过多，同样会让产品不可用。

## 设计一份可维护的评测案例

评测案例不要只有问题和标准答案。它还需要固定环境、允许路径和禁止行为：

```typescript
interface AgentScenario {
  id: string;
  description: string;
  datasetFixture: string;
  userGoal: string;
  userContext: {
    roles: string[];
    locale: string;
  };
  expected: {
    outcome: 'completed' | 'clarification' | 'denied' | 'failed';
    planAssertions?: PlanAssertion[];
    requiredTools?: string[];
    forbiddenTools?: string[];
    factAssertions?: FactAssertion[];
    safetyAssertions?: SafetyAssertion[];
  };
  budgets: {
    maxModelCalls: number;
    maxToolCalls: number;
    maxLatencyMs?: number;
    maxEstimatedCost?: number;
  };
}
```

一个正常案例可以写成：

```json
{
  "id": "sales-by-channel",
  "datasetFixture": "sales-small-v1",
  "userGoal": "统计华东各渠道销售额",
  "expected": {
    "outcome": "completed",
    "requiredTools": ["run_pivot"],
    "forbiddenTools": ["export_report", "send_email"]
  },
  "budgets": {
    "maxModelCalls": 3,
    "maxToolCalls": 2
  }
}
```

评测集应覆盖四类任务：

1. **主路径**：常见且应该稳定完成的任务。
2. **边界路径**：空数据、零值、日期边界、字段缺失。
3. **歧义路径**：多个同义字段、范围不清、目标过宽。
4. **对抗路径**：注入文本、越权字段、写操作绕过确认。

只测试快乐路径，会让完成率看起来很高，却无法说明系统遇到真实用户输入时怎样表现。

## 计划比较前先规范化

模型可能生成语义相同但顺序不同的计划：

```json
{ "rows": ["channel"], "filters": ["region=华东", "year=2026"] }
```

与：

```json
{ "filters": ["year=2026", "region=华东"], "rows": ["channel"] }
```

直接比较 JSON 字符串会产生无意义失败。评测前可以：

- 补齐默认值。
- 按稳定键排序不影响语义的数组。
- 将字段别名转换成稳定 ID。
- 统一日期和数字格式。
- 去除展示用摘要等非执行字段。

然后对关键语义做断言：

```typescript
expect(plan.rows.map((item) => item.field)).toEqual(['channel']);
expect(plan.measures).toContainEqual({
  field: 'revenue',
  aggregation: 'sum'
});
expect(plan.filters).toContainEqual({
  field: 'region',
  operator: 'eq',
  value: '华东'
});
```

评测要允许不影响任务的表达差异，同时严格限制会改变结果的差异。

## 确定性测试、轨迹测试与端到端评测

三种测试解决不同问题。

### 确定性单元测试

使用假模型和假工具，验证：

- 最大步骤和超时会终止循环。
- 错误分类触发正确重试策略。
- 未授权工具无法执行。
- 事件 reducer 能处理重复和乱序。
- 幂等回执不会产生第二次写入。

反馈快、结果稳定，适合每次提交运行。

### 轨迹回放测试

保存经过脱敏的模型决策和工具结果，跳过真实外部调用，重放整条轨迹：

```text
固定模型决策 + 固定工具结果
              ↓
      新版本运行器与前端 reducer
              ↓
       检查状态和最终呈现
```

它适合验证运行器、错误处理和 UI 改动是否破坏旧任务。由于没有重新请求模型，它不能衡量新 Prompt 或新模型质量。

### 在线模型评测

使用固定数据集和真实模型重新运行场景，评估计划、轨迹、答案、成本和延迟。这类评测有波动，也有费用，适合定期运行或在重要模型、Prompt 变更时运行。

可以对每个场景重复几次，报告通过率和分布，而不是只记录一次结果。

## 模型评分可以用，但不能单独用

自然语言报告的清晰度、相关性和完整性很难全部写成规则，可以引入评分模型：

```text
输入：用户目标、允许使用的事实、待评分报告
输出：
- 是否回答目标
- 是否存在无事实支持的结论
- 是否忽略关键警告
- 解释是否清晰
- 引用失败的具体片段
```

为了减少评分漂移：

- 评分标准要具体，不要只问“回答好不好”。
- 给评分模型提供原始事实，而不是只看答案。
- 使用少量人工标注案例校准评分。
- 固定评分模型版本和配置。
- 对发布门禁优先使用代码断言。

评分模型本身也是概率系统。它适合补充难以量化的质量判断，不适合作为金额正确、权限合法这类硬规则的唯一裁判。

## 用指标定位失败发生在哪一层

一个总完成率无法指导优化。可以建立漏斗：

```text
1000 次任务
  ├─ 940 次计划结构合法
  ├─ 880 次领域校验通过
  ├─ 850 次工具执行成功
  ├─ 830 次报告事实校验通过
  └─ 810 次用户未立即修改或重试
```

不同下降位置对应不同解决方案：

- 结构合法率下降：检查模型适配器、Schema 和输出提示。
- 领域校验失败增多：检查字段目录、别名和业务协议。
- 工具成功率下降：检查依赖、超时和数据规模。
- 忠实度下降：检查 Evidence 结构和报告约束。
- 用户修改率高：可能是任务理解或交互预览有问题。

没有分层指标时，所有问题最后都会被归因成“模型不够好”。

## 为版本变化建立对照实验

每次评测至少记录：

- 模型供应商与模型名称。
- Prompt / 配置版本。
- 工具定义版本。
- 计划 Schema 版本。
- 数据集 Fixture 版本。
- 代码提交或构建版本。

比较两个版本时，尽量只改变一个变量。例如只升级模型，保持 Prompt、工具和数据集不变；或者只修改工具说明，使用同一模型。

输出报告不要只看平均分，还要列出：

- 哪些原本通过的场景失败了。
- 哪些失败场景得到修复。
- 延迟和成本分布如何变化。
- 安全案例是否全部保持通过。

平均完成率从 82% 升到 84%，但一个高风险确认案例从通过变成失败，不能简单判定新版本更好。

## 发布门禁应该分级

不是所有指标都需要 100%，但硬边界必须明确。

例如：

```text
阻止发布：
- 任一越权或确认绕过案例失败
- 确定性聚合结果不正确
- 幂等写操作产生重复副作用

需要评审：
- 主路径完成率下降超过 2%
- P95 延迟增加超过 20%
- 单任务平均成本增加超过 15%

仅记录趋势：
- 报告文风偏好
- 非关键解释完整度
```

安全、权限和事实正确性不能用其他平均分抵消。

## 线上监控与离线评测要闭环

离线任务集永远覆盖不了全部真实表达。线上可以收集不含敏感内容的信号：

- 用户是否立即重试或改写问题。
- 是否手动修改模型生成的计划。
- 哪类澄清问题最常出现。
- 哪些工具错误突然上升。
- 用户在哪个阶段取消。
- 哪种数据规模导致超时。

经过隐私审查和脱敏后，把高频失败模式转成新的固定案例：

```text
线上失败 → 人工归类 → 新增脱敏 Fixture → 加入回归评测 → 修复 → 观察线上指标
```

这比只在模型升级时临时试几个问题更能持续提高可靠性。

## 第一季最终架构

经过八篇文章，本季得到的不是一个万能 Agent 框架，而是一组可以复用的边界：

```text
用户目标
  ↓
架构判断：函数 / 工作流 / RAG / Agent
  ↓
模型生成结构化计划
  ↓
Schema + 领域规则 + 权限 + 预算校验
  ↓
工具注册表与策略层
  ↓
必要时澄清、预览和人工确认
  ↓
确定性领域引擎执行
  ↓
结构化事实与证据
  ↓
模型组织报告
  ↓
前端状态、事件、取消与恢复
  ↓
轨迹、指标和回归评测
```

贯穿整个架构的原则始终没有变化：

> 概率性组件负责处理模糊语义，确定性组件负责事实、权限和副作用。

## 最后

Agent 最吸引人的地方，是它可以在不确定路径里动态选择动作；最危险的地方，也正是这种不确定性容易被自然语言的流畅外表掩盖。

当系统能够保留完整但克制的轨迹，把计划、工具、事实、回答和安全分层评测，并用线上失败不断补充回归案例时，我们才有能力判断一次改动究竟带来了进步还是新的风险。

演示回答“它能不能做一次”，评测回答“它能不能持续做对”。后一个问题，才决定 Agent 能不能真正进入产品。
